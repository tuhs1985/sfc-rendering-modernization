# Run231 — runtime checks and diagnostic-only candidates

Current-source audit of the prepared **native multi-ship replacement/performance** path, following Run229 gameplay and Run230's reproduced projection defect. Read-only audit: no runtime/configuration changes, builds or new gameplay. This supplements the historical [pipeline audit](pipeline-work-and-diagnostics-audit.md); historical switches must not be mistaken for current behavior.

The recommended split is not simply “validation on/off.” Some checks can become nonblocking diagnostics; others belong once per frame, imported resource, asset revision or build. Functional identity and GPU ownership must remain. A feature temporarily lacking an update should not automatically veto unrelated valid geometry.

## Additional timing heuristic,not a data-validation check

**C15 — first-asset bootstrap's fixed24Presents.** `d3d9_direct_host.cpp` sets24 startup Presents and sleeps10ms on each iteration;ordinary live updates use one Present. This includes at least240ms of explicit sleeps plus actual startup rendering/API work. It is explicitly described in source as a transitional compatibility policy,not NVIDIA-required readiness. Historical Run160 found incomplete appearance after reducing it. It should be re-evaluated against the current supported material-readiness path,not silently deleted or treated as a permanent correctness rule. It affects startup/new activation,not ordinary camera-switch reloads. Exact contribution to current first-image timing is unmeasured.

## New light-gate evidence

The six-ship host logs actual `LIGHT_INPUT_UNAVAILABLE` for frames2083,4033,4272,4414,4646. Each is exactly the first frame of a reviewed timeout burst of13,7,11,9,13frames respectively. This confirms five whole-input rendering vetoes. It does **not** prove that one light veto alone accounts for every following timeout in each burst;subsequent scheduling/output behavior remains distinct.

`DirectLights::update` can fail on an in-progress shared cell,missing loaded packet,header/session/context mismatch or the underlying light validity rules. Those rules include future-frame rejection,30-frame/half-second freshness,checksums,normalization and allowed values. The log does not retain the precise reason for the five failures. Keep valid light semantics;decouple transient light availability from whether valid geometry is rendered.

Evidence and current source hashes: `artifacts/player-replacement/run231/audit-evidence.json`. The sampled source data on all90steady timeouts arrived within0.1798ms;none of the unmeasured CPU checks should be called a multi-millisecond bottleneck without profiling. A false-rejection chain can be much more damaging than the direct CPU time of the check itself.

## Keep functional

- Session/owner epoch/model-source/revision/frame/output matching and actual per-owner rendered membership.
- Atomic coherent publication,complete transfer acknowledgement,packet bounds and finite required values.
- Geometry/index/group bounds and supported source-format checks at admission.
- Owner lifetime/retirement and model/LOD change handling;cheap readable-identity checks protect source memory access.
- Actual native caller/list/manager validation before suppression;capture-before-suppression,original argument preservation and state restoration.
- GPU completion,slot ownership,lease protection through all owner reads,resource/device epoch changes,stop/unload coordination and failure handling.
- Deadline/queue policy remains functional timing policy,not diagnostic validation. Adjusting Strict/ExtraFrame cannot repair a rejected scene input.
- Copied-install/process-path checks and explicit memory/output limits. Current1920×1080/8MSAA constraints are qualified capability limits,not proof checks that can simply be disabled.

## Already off in performance mode

Native VB/IB upload readback comparisons,texture GPU pixel readback comparisons,detailed renderer CSVs,continuous scene/light JSONL mirrors,lifecycle journals and sampled frame dumps are already test-only/off. High-volume geometry hooks,broad draw tracing,continuous screenshots and shield replay are not active in the native replacement baseline. Do not count those as new savings. Light/texture conversion settings are appearance features,not diagnostics;this audit does not authorize changing the sponsor's appearance baseline.

## Suggested implementation order

1. C01/C02 false projection gates;C03 light availability must not veto valid geometry;C04 calibration evidence must not poison functional publication.
2. C05/C06 selectable detailed evidence and C07 unused callback registration.
3. C08–C10 cache expensive repeated validation at the proper change boundary while retaining cheap matching.
4. C11–C15 startup/new-asset/deployment cleanup separately,so camera-transition measurements are not confused with startup speed.
