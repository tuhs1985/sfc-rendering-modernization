## Supported findings

The accepted executable loads eighteen shared damage images: light, medium and
heavy, each with a companion image, for standard ships, starbases and organic
models. All inspected originals are 256 by 256 uncompressed 24-bit BMPs. They
contain no stored alpha channel. Resource acquisition uses the established
registry at `0x008CC620`, virtual slot `+8`; resulting IDs are stored in adjacent
tables. IDs are runtime resources, not pointers or permanent image identities.
The [metadata inventory](evidence/20261103-damage-texture-path.json) records all
names, request sites, destination slots and original file hashes without image
or executable contents.

`tModel0` rendering at `0x0042E4B2` draws the ordinary polygon list from
`model+0x14` first, returning from the wrapper at `0x0042E55D`. It then derives
a three-level selection from its third argument: integer conversion of
`4*x + 0.5`, minus one, capped above at two. A negative result skips the damage
branch. The fourth argument chooses the adjacent image family: standard=0,
starbase=1, organic=2, supported by the filename-to-table assignments. The
precise gameplay meaning/range of the upstream scalar is not independently
qualified merely by this formula.

For the enabled branch, virtual model slot `+0x3C` resolves to `0x0042EB52`.
It lazily creates `model+0x18`: a second polygon-pointer array with the same
polygon count (`model+0x10`). It copies polygon normals and corner position
indices, uses group zero for a shared damage material, and gives the copied
corners separate UV values derived from model-space positions and face-normal
projection. These are not simply the original diffuse texture coordinates.
Construction is skipped when the secondary array already exists. The model
destructor frees this array and its corner allocations.

The render function installs a temporary material descriptor (flags `0x23`,
white packed colour, scalar fields including 0.3 and 1, selected damage pair),
then submits the secondary list to manager slot `+0x140`, which resolves to
the existing wrapper `0x006AC5A0`. Its return address is `0x0042E626`.
Manager slot `+0x13C` stores the descriptor pointer at `manager+0x558`.
This pointer may refer to the rendering function's stack: any observer must
copy its required values before the call returns, not pass the pointer to a
worker. Flags `0x23` alone do not establish a specific blend equation.

This supports the sponsor's description of an extra damage layer over the
ordinary hull. The sponsor additionally confirms pure black is transparent.
The exact native colour-key/alpha-test/blend interaction, filtered edge
behaviour and companion-image contribution remain to qualify. A 24-bit source
file does not rule out alpha generated by the texture loader. Do not confuse
the wrapper's alpha-test state with alpha blending, or turn all black hull
markings transparent. Any transparency conversion belongs only to this
qualified damage path.

## What the previous captures contain

Examined 100 locally available `M1-A-events.csv` files under the M1 runs and
game-run gate folders. Fifty contain 26,365 model-entry samples; their recorded
third argument is zero, with no retained secondary-wrapper rows. These are
sampled/bounded historical logs, not complete damage histories. They do not
prove the associated battles lacked damage. Detailed metadata is in ignored
`artifacts/player-replacement/run282/historical-model-arguments.json`.

The two Run172 broad rendering reviews retain downstream state/resource epochs
and call chains, but contain no explicit `0x0042E626` producer join. Their
bulk geometry/images were deliberately excluded. This evidence does not supply
a damage-layer mesh or an exact damage blend receipt.

Current `m1_mesh_export.h::capture_mesh` and `m1_live_scene.h::observe` admit
only primary caller `0x0042E55D`; fresh retained packets therefore omit the
secondary damage polygons and their selected temporary material. Suppression
already recognizes primary and secondary lists; recognition for suppression
does not mean the secondary data is transported to Remix.

## Smallest next observation and interface work

1. Reuse existing model-entry/wrapper observations, owner epochs and current
   material-pointer location. Record the two scalar/family arguments, both
   list identities and selected material values together, before suppression.
   Snapshot a secondary mesh once after native lazy construction, including
   its own corner UVs and resolved image associations. Keep the geometry hook
   disabled and do not dereference these native pointers after the callback.
2. Correlate that damage submission with its actual native blend/alpha-test/
   texture-state path and resource identity. Pure black transparency is already
   established from the sponsor's authoring experience; qualify its implementation
   and companion-image use without inventing an opacity formula. Existing
   asset resolution can supply original files; no GPU screenshot/readback or
   substitute texture is needed for the eighteen known images.
3. Keep reusable damage mapping separate from per-owner severity/family state.
   Two ships sharing a hull must retain independent damage. Send changes rather
   than rebuild the hull or regenerate images every frame.
4. Respect native insertion ordering: the primary commit happens before the
   first lazy secondary list is constructed. Observing the secondary call later
   cannot retroactively change an already inserted image. Qualify first-use
   preparation and the corresponding source-frame damage state before enabling
   display; do not silently apply stale state or assume the secondary pointer
   is valid at initial model entry.

The next runtime observation should be a narrow damaged-hull checkout only
after the missing fields are captured. No broad survey or additional discovery
trace is justified by this initial investigation. Break models remain separate.
