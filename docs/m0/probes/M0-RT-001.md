# M0-RT-001 — Internal Render-Path Correlation Probe

## Question

Do the exact-build engine scene functions, native IDirect3DDevice3 indexed-draw
flush, and DirectDraw presentation path execute in a stable order during a
tactical scene, and can engine-side pointers be observed above the draw-call
boundary?

## Static basis

The supported client is StarFleetOP.exe 2.5.6.4, MD5
2BE8F713F81B1C68D50EAD6088C32886. SDK GUID and vtable correlation establishes:

| Wrapper member | Interface or role | Static evidence |
|---|---|---|
| +0x30 | primary IDirectDrawSurface4 | created through IDirectDraw4::CreateSurface |
| +0x34 | back-buffer IDirectDrawSurface4 | obtained/created during surface setup |
| +0x38 | active render-target surface | selected from primary/back buffer |
| +0x3C | z-buffer IDirectDrawSurface4 | created then attached to +0x38 |
| +0x40 | IDirect3DDevice3 | IDirect3D3::CreateDevice output |
| +0x44 | IDirect3DViewport3 | IDirect3D3::CreateViewport output and device AddViewport |
| +0x48 | IDirectDraw4 | QueryInterface with IID at 0x007BB1C8 |
| +0x4C | IDirect3D3 | QueryInterface with IID at 0x007BB198 |

This corrects the Pre-M0 interpretation of 0x006A8500: IDirectDraw4 vtable
+0x28 is FlipToGDISurface, and the function is used from the window-message
path. It is not BeginScene.

The actual engine scene functions are:

- 0x0069E300: nested scene-begin owner; calls IDirect3DDevice3::BeginScene at
  0x0069E36A.
- 0x0069E3D0: nested scene-end owner; flushes pending geometry through
  0x006AB380, then calls IDirect3DDevice3::EndScene at 0x0069E41B.
- 0x006AB380: pending geometry flush; issues IDirect3DDevice3
  DrawIndexedPrimitive at 0x006AB3C0 or DrawPrimitive at 0x006AB3D9.
- 0x0069EB90: engine present owner; calls wrapper present at 0x0069EBD7.
- 0x006A84B0: wrapper present; chooses IDirectDrawSurface4 Flip or Blt.

## Probe method

The external 32-bit debugger attaches to an already-running exact-hash client.
It places temporary software breakpoints in process memory only; it does not
modify StarFleetOP.exe or any asset on disk. It records hit order, register
state, selected structure members, batch counts, vertex/index pointers, device
and surface pointers, and the candidate ship/model/parser events.

The probe refuses any executable whose MD5 differs from the supported build and
also validates the original first byte at every probe address before arming.

## Probe points

| ID | Address | Captured meaning |
|---|---:|---|
| ship_model_init | 0x0041C271 | candidate ship/model object pointer and first arguments |
| model_parse | 0x0042FEF9 | model object/parser pointer and first argument |
| scene_begin | 0x0069E300 | manager, Device3, wrapper, scene depth |
| scene_end | 0x0069E3D0 | manager, Device3, wrapper, scene depth |
| engine_present | 0x0069EB90 | manager and presentation-side pointers |
| batch_flush | 0x006AB380 | batch object, Device3, vertex/primitive counts and mode |
| draw_indexed_call | 0x006AB3C0 | native Device3 call arguments, vertex/index pointers and counts |
| geometry_submit | 0x006AB410 | manager entry caller and four submission arguments before batching |
| surface_present | 0x006A84B0 | primary/back/render-target surfaces and flip/blit mode |

## Sponsor action

No assembly interpretation is required. The prepared test consists only of
starting the game through SFC Launcher with the same configuration already
known to reach gameplay, opening a tactical scene, keeping it active long
enough to exercise camera or ship control, and closing it after the log has
been produced. The runner waits for and attaches to the launcher-created
StarFleetOP process; it does not launch the client directly or select a
rendering configuration.

## Safety and stop conditions

- No persistent executable modification.
- No change to gameplay state, save files, requirements, or rendering stack.
- Breakpoints automatically saturate to cap high-frequency overhead.
- The debugger detaches after its bounded time window and restores every armed
  byte before detaching.
- Ambiguous or missing tactical correlation is a failed probe result, not
  evidence of success.
