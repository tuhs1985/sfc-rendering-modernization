# Native insertion synchronization — recommended first implementation

Run225, 2026-10-31. Read-only assessment against commit `0c82e01`, Run224 runtime evidence, bundled ReShade headers and Microsoft graphics documentation. This records a recommended qualification path; no rendering policy, native hook or synchronization implementation has changed.

## Decision

First qualify a **bounded, event-driven frame gate before the first selected ship mesh submission**, after original capture has published the frame and before any original polygon count is suppressed. When exact matching game-usable output is acquired, finish already queued native work, insert colour and physical depth into the native scene, then forward the selected zero-count submissions and let SFC draw later effects normally.

The gate belongs to a separate insertion coordinator on the native rendering thread, outside `RecordHook`, its capture critical section, and D3D/ReShade graphics callbacks or held engine/driver locks. Capture remains observation/publication-only. This still deliberately pauses SFC's render thread: it is a **new optional synchronization contract** that must be qualified, not a relabeling of the existing nonblocking guarantee or a performance-neutral change.

Waiting at the selected visual exit **after suppression** is an inferior first design: timeout would occur after the original geometry had already been omitted. Moving the decision ahead of suppression preserves a complete original render on a failed admission without trying to rebuild already lost drawing. Successful insertion and a retained output lease must precede suppression authorization.

## Alternatives assessed

| Path | Supported mechanism / current fit | Decision |
| --- | --- | --- |
| Bounded CPU event gate before suppression | Existing private worker completes a GPU fence before game-pool READY. Native capture publishes inputs before SFC Present. A finite readiness/stop/process wait can end before changing drawing. | Recommended first qualification. Explicit render-thread latency; measure actual frame delivery. |
| GPU-side fence wait before insertion | D3D11 Context4 supports GPU Wait/Signal; D3D11 Device5 supports shared fences. Avoids a blocking CPU wait. | Valuable optimization candidate, not the first implementation with current protocol. Requires an output surface/value reservation before pixels are ready and a renderer-loss/cancellation design. |
| Retain all subsequent native drawing in command lists | D3D11 deferred contexts support recorded command lists. SFC/dgVoodoo currently uses the immediate path; existing immediate work is not automatically turned into deferred commands. | Larger capture/forwarding/resource-lifetime change. Do not recreate all-effect replay to solve the first ship. |
| Extract alpha/layers from the finished frame | Our retained native colour contains already blended contributions, not a complete layer stack. | Does not recover the required order. Parked shield replay is not resumed. |
| Late overlay or previous-frame ship over current native scene | Existing late return is tested, but foreground ordering or source-frame correspondence fails. | Preserve as historical diagnostic only; not the replacement repair. |

## What the supported APIs establish

- [ID3D11Fence::SetEventOnCompletion](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_3/nf-d3d11_3-id3d11fence-seteventoncompletion) supplies completion notification. Our `worker_gpu_fence.h` already uses it with a Windows event on owned workers. Reuse the completion mechanism; do not copy its five-second worker timeout into SFC's render thread.
- [ID3D11DeviceContext4::Wait](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_3/nf-d3d11_3-id3d11devicecontext4-wait) queues a dependency on a fence value on an immediate context. It is equivalent to [D3D12 command-queue Wait](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandqueue-wait), which returns immediately while future GPU work waits. The D3D11 Wait signature has no timeout argument. This is a useful primitive, not a complete bounded-disconnect policy.
- [Context4::Signal](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_3/nf-d3d11_3-id3d11devicecontext4-signal) signals after previous work. [CreateFence](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_4/nf-d3d11_4-id3d11device5-createfence) and [OpenSharedFence](https://learn.microsoft.com/en-us/windows/win32/api/d3d11_4/nf-d3d11_4-id3d11device5-opensharedfence) provide the supported sharing path. Our current worker fence is private (`D3D11_FENCE_FLAG_NONE`), not already a shared inter-process scheduling fence.
- [Immediate and deferred rendering](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-render) distinguishes commands queued on the immediate context from commands recorded using a deferred context. [ExecuteCommandList](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-executecommandlist) can restore context state. Neither automatically intercepts and defers all existing SFC drawing.
- The bundled ReShade SDK documents draw callbacks before native Draw/DrawIndexed and permits suppressing those calls. That is useful for graphics observation; it does not establish owner-exclusive SFC batches, expose a universal pre-UI event, or justify waiting while inside those graphics callbacks.

## Source findings supporting the gate

1. `m1_component.cpp` observes original lists and calls `updatePersistent` at the polygon wrapper before applying count-zero suppression. `RecordHook` holds `g_lock` during this work, then releases it and decrements its recorder counter. **No wait may be added there.** A separate coordinator needs its own registration/reentrancy/drain lifetime if invoked after the recorder returns; the old recorder count does not protect that new call from unload.
2. `LiveOwnerInput::next` consumes the published input mailbox. `input_admission.h` accepts the current frame, subject to identity/clock/bad-frame and existing buffered age checks. The consumption watermark closes old frames; it is not a requirement to reach SFC Present before rendering. Holding SFC at the published frame is therefore not a source-code circular dependency. Driver/device/worker progress must still be tested.
3. `GameOutputWriter::publish` requires a valid native frame receipt but does **not** require its Suppressed flag or Active mode. The passive startup fix already proved output can be produced while original drawing remains authorized. The new gate must preserve this independence; do not make readiness depend on the decision readiness is supposed to authorize.
4. `output_receiver.cpp` copies the output, completes its GPU fence, then publishes the game pool. This is the actual readiness edge to notify. The upstream packet publication stamp is too early to serve as that notification.
5. Current output slots are reserved in `GameOutputWriter::copy` after renderer output arrives. GPU-side waiting would need earlier immutable slot/fence assignment. Existing READY/idle ownership cannot simply be reused as an advance promise that the correct frame will eventually occupy a surface.
6. Existing native flush `006AB380` submits previously queued primitives and resets batch counters. It is shared. Any deliberate closure before insertion must be qualified for manager state, empty/pending batches and exact ordering; **never suppress at that shared flush**. No direct invocation is implemented or declared safe by this assessment.
7. Existing `DepthCompositor` writes real colour/depth, but its BGRA-only resource and raw GetDevice checks do not yet qualify Run224's actual RGBA8 TYPELESS/linear-view 8MSAA target. Keep the physical hull output and current appearance; qualify format/device/state handling rather than editing images or depth bias.

Source-check script and hashed references: `artifacts/player-replacement/run225/review_sources.py`, `source-review.json`. Ten checks and copy→fence→publish ordering validated. No native executable or GPU campaign needed for these source relationships.

## Intended transaction, before gameplay implementation

1. Precreate insertion resources, notifications and coordination state in a distinct default-off mode. Its recorder publishes original data but bypasses the existing in-recorder suppression block. Its receiver disables old late composition/authorization; do not let the old path suppress a list before the new gate runs. Preserve current-user/session ownership and existing output/memory budgets. Keep native/adapter/renderer configurations and lifecycle machinery.
2. Original capture publishes a coherent frame ticket: session, owner epoch, asset revision, source sequence/frame, camera/pose or cohort hash, activation generation and device/resource epoch. No guessed frame advancement or imposed refresh cap.
3. After capture returns and before the first qualified selected list is forwarded, the separate coordinator checks an exact matching output lease. If needed, wait on readiness, stop or renderer exit with **one absolute frame deadline**, not repeated renewed timeouts, fixed sleeps or busy loops. Wakeups are not authorization; recheck identity, readiness, deadline and ownership.
4. Do not wait while owning capture, engine or graphics locks. Verify independent renderer/admission/import worker progress during the gate. On failed admission, leave this frame's native drawing intact before any suppression. Repeated misses during ordinary play fail the experiment; frequent fallback is not a successful synchronization solution.
5. Once a valid completed output is leased, establish prior native batch closure and compatible active colour/depth targets. Submit the depth-writing insertion with state restoration. Only then authorize the selected count-zero primary/secondary submissions, using one consistent frame decision. Validate both lists/source identity ahead of changing the first submission.
6. Maintain the lease until the game's GPU has finished reading it, using the existing read-lease/fence approach. Renderer disconnect after a completed lease must not recycle the image under SFC. SFC continues ordinary effects, text and presentation; disable the old late returned-ship pass for this mode.
7. Stop wakes pending gates, revokes new requests and drains both capture and coordinator callbacks before unloading either component. Preserve safe original drawing when no replacement was committed; never free a queued image or leave a partly suppressed frame on a failure path.

The common contract is **frame ticket → completed output lease → insertion receipt**, not a Remix-specific sleep. D3D11 is the current return adapter; the D3D9 input adapter and Remix rendering remain. Future D3D12 submission/return adapters can implement the same ownership/identity contract with their supported fence interfaces. This does not claim interchangeability is already complete.

## Smallest next increment and acceptance

Build an isolated default-off qualification fixture first, reusing the existing native depth-compositor tests and genuine return transport. Exercise the event gate before a synthetic native mesh decision, with later native depth-tested effects and depth-disabled text drawn normally—not captured/replayed. Use Run224 delays as test cases plus late, malformed, wrong-frame, disconnected, stopping and slot-reuse cases. Record actual game-pool fence completion/READY and insertion completion, not only upstream publication.

Qualify the native batch-closure call/ABI and pre-suppression boundary separately before connecting it to SFC. Validate no first-list suppression on failed readiness, consistent primary/secondary decisions, state preservation, no capture-lock wait, reentrancy and unload drain. Original assets/settings remain untouched; no broader scene replacement or appearance work.

Choose the first live deadline from actual completed-output and remaining-native-work measurements. Run224's median14.6ms model-exit→Present gap is not proven spare capacity; a fixed9ms sleep is not acceptable. Compare real frame-time distributions and rare misses against the original path. First player checkout must show one correctly aligned ship with natural shield/text occlusion, normal gameplay and controlled cleanup, without ordinary-camera repeated fallback. If it cannot do so within the frame budget, report that measured limit and evaluate the reserved-surface shared-fence alternative; do not expand shader replay or silently relax matching.

No new gameplay capture is needed to repeat the timing discovery.
